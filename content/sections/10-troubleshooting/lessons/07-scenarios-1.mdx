**By the end of this lesson you will be able to:**

- work a ticket about activation, an offline branch or a flapping link from symptom to fix;
- choose evidence in order and say what each piece can and cannot prove;
- build a short hypothesis tree and test each branch with a read-only observation;
- say where each fix lives and how you verify it.

All tickets are invented. Every box labelled **schematic** is **illustrative**: it uses only field names the documentation prints, with made-up values, and is not real output.

## Ticket 1: the new Edge in Leeds will not come online

**Ticket (user's words).** "We plugged in the new box on Tuesday and the light is on but it never shows up. Nothing works at the branch."

**What we know.** One new Edge, a day old. **What we do not know.** Whether it ever reached the Orchestrator, which activation method was used, whether the link has an address.

**Layer decision.** <Term id="activation">Activation</Term> and management, with the <Term id="underlay">underlay</Term> just below it: an Edge that never activated cannot be tested with Remote Diagnostics, which needs the connection the Edge sets up at activation. So the evidence is events, the Edge's entry in the VCO, and what a person on site can see.

**Evidence, in order.**

1. The Edge's entry under **Configure > Edges**: its state, and that it was created with a model, a Profile and, optionally, a serial number the Edge must present. An activation key expires after one month if unused.
2. **Monitor > Events** for this Edge: an activation event with a time.
3. On site: is the link up, does the Edge have an address? Push (auto) activation needs outbound Internet through DHCP; pull activation needs the email to be acted on.

| Event seen | Documented meaning |
|---|---|
| Activated | the Orchestrator successfully activated the Edge |
| Activation failed | the activation link was incorrect, or the configuration could not be downloaded |
| Activation incomplete | activation completed but a software update failed |
| none at all | the Orchestrator never heard from the Edge (not a documented event; our reading) |

```text
schematic (illustrative, not real output)
event            displayed as        severity  generated by
MGD_ACTIVATION_ERROR  Activation failed  ERROR   Edge (MGD)
```

**Hypothesis tree.**

- No event at all: the Edge has no route to the Orchestrator (link, address, DHCP, a proxy or firewall); test by asking site for the link state and address.
- "Activation failed": the key or link is wrong, or the serial number does not match; test by comparing the key and serial in the VCO with what was used.
- "Activation incomplete": the software update step failed; test by reading the event time and trying again after the link is stable.

**Fix and where.** Correct the one cause: a new activation from the Edge's entry in Configure > Edges (the exact control is to confirm in your VCO), or a working link on site.

**Verification.** The events show Activated, the Edge is Connected, and a Remote Diagnostics test such as Interface Status now runs on it.

**Lesson learned.** An Edge that never activated has only events and people on site as evidence.

## Ticket 2: the Manchester branch went offline

**Ticket.** "Everything at Manchester is down since 08:10. The phones, the till system, all of it."

**What we know.** One branch, a start time. **Not known.** Whether the Edge or the ISP is down.

**Layer decision.** Activation and management first: is the Edge still connected? Scope is one branch, so the LAN, the Edge's power and the WAN links are the suspects before any shared component.

**Evidence, in order.**

1. Events around 08:10: **Edge Down** is raised by the Orchestrator when the Edge misses two or more consecutive <Term id="heartbeat">heartbeats</Term>; **Link Down** says a WAN link lost its connection to the Edge or the Edge service; **Edge Service Down** says the Edge service may be down.
2. Other branches on the same ISP or Gateway: are they fine? (This narrows to one branch.)
3. An HA pair: **Edge HA Failover** events show whether the standby took over.

| Reading | Hint it gives |
|---|---|
| Link Down on every link, then Edge Down | the site lost all its WAN links or power |
| Edge Down with no Link Down | the Edge stopped reporting; look at power and the Edge service |
| Edge HA Failover, then calls work | the standby took over; find why the active failed |

```text
schematic (illustrative, not real output)
08:10:03  Link Down   Manchester Edge  ALERT
08:10:05  Link Down   Manchester Edge  ALERT
08:10:21  Edge Down   Manchester Edge  ALERT
```

**Hypothesis tree.** (a) Both ISP circuits down: confirm with the ISP and by seeing Link Up events return together. (b) Power or hardware fault: the Edge never returns. (c) A change at 08:00: check who changed what.

**Fix and where.** Mostly outside the VCO: restore the circuit or power. When the Edge returns, the VCO shows Link Up and Edge Up.

**Verification.** Edge Up, Link Up, then List Paths shows the tunnels Stable.

**Lesson learned.** When the Edge is not connected the VCO shows when and what it last saw; it cannot run tests.

[Reproduce a link going down in the simulator](/sim/hub-and-spoke-demo/monitor): the Monitor screen shows how a down link changes the tunnels. Which events a real VCO raises is not modelled.

## Ticket 3: the Bristol Internet link keeps dropping

**Ticket.** "Video calls at Bristol break up every few minutes and then recover on their own."

**Known.** One branch, repeated, self-healing. **Not known.** Cable, ISP or something else.

**Layer decision.** The WAN link (underlay), then quality. A link that comes and goes is an underlay symptom until proven otherwise.

**Evidence, in order.**

1. **Monitor > Events**: the pattern of Link Down and Link Up, and the Edge's own Link dead, Link alive, Link usable and Link unusable events. "Dead" and "unusable" are different states.
2. **Interface Status** (Remote Diagnostics): link detected true or false, and RX and TX errors; the guide says errors that keep increasing point to replacing cables or SFPs, and that the values should not increase when you run the test twice.
3. **List Paths**: a state other than Stable means an issue with the WAN link; Unstable means loss, jitter or latency.

```text
schematic (illustrative, not real output)
Interface Status   link detected: true   RX errors: 1204   TX errors: 0
Run 2 (a minute later)                   RX errors: 1873   TX errors: 0
```

**Hypothesis tree.** (a) Physical: RX errors increasing, so cable or SFP; test by running the test twice and by checking the cable. (b) ISP: no errors on the Edge, link events still repeat; test by comparing with the ISP's line check. (c) Quality only: link stays usable but List Paths shows loss; that is a DMPO question (Lesson 9).

**Fix and where.** Replace the cable or SFP, or open a case with the ISP. No documented VCO setting fixes a flapping link; the sources read give no flapping-specific guidance.

**Verification.** RX errors stop increasing, no Link Down for a day, List Paths Stable.

**Lesson learned.** Run the same read-only test twice; the change between runs is the evidence.

## What you would see in the VCO

- **Configure > Edges** (the Edge's entry), **Monitor > Events**, **Monitor > Edges** Links and Paths tabs.
- **Diagnostics**: Interface Status and List Paths.

<Callout variant="tip" title="Check this in your own VCO">
  - **[observation candidate]** Open: Monitor > Events for an Edge you activated. Expect: an Activated event with a time. Docs may differ: the displayed name.
  - **[observation candidate]** Open: Configure > Edges, a not-yet-activated Edge. Expect: a state that says it is not activated and an activation key. Docs may differ: the wording and where the key is shown.
  - **[observation candidate]** Open: Monitor > Events when you pull a WAN cable in a lab. Expect: Link Down and later Link Up. Docs may differ: delay and which events appear.
  - **[observation candidate]** Open: Diagnostics, Interface Status run twice a minute apart. Expect: stable error counts on a healthy link. Docs may differ: the field names.
</Callout>

## Key takeaways

- Without an activated, connected Edge the evidence is events and people on site.
- Read the pattern of Link and Edge events, not just the last one.
- Run read-only tests twice and compare.
- Fixes for these tickets are mostly outside the VCO; the VCO verifies them.

## What would you look for in the VCO

- Which event first shows the problem, and who generated it?
- Is the Edge Connected, so that Remote Diagnostics can run?
- What changed between two runs of the same test?
