# Decision log

## Decided

| # | Decision | Notes |
|---|----------|-------|
| 1 | Frontend: React + TypeScript + Vite + Tailwind CSS | Strict TS. |
| 2 | Backend: Go, `net/http` + chi, pgx, plain SQL migrations, no ORM | Embedded migration runner (small custom one, tracked in `schema_migrations`, guarded by an advisory lock) instead of golang-migrate, to avoid an extra dependency. `.down.sql` files are kept for reference but are not executed by the runner. |
| 3 | Database: PostgreSQL 16 in Docker via docker-compose | Named volume, healthcheck; backend waits for healthy DB. |
| 4 | Single-user, local only | No login or accounts; one implicit profile; no `user_id` columns. Ports bind to 127.0.0.1. |
| 5 | Course content lives in `/content` files, never in the DB | DB stores progress only. Mounted read-only into the backend. |
| 6 | Simulation engine will be written in Go in the backend | Later step. |
| 7 | Dev API access via Vite proxy rather than CORS | Same-origin from the browser's view. |
| 8 | Soft-gating: quizzes never block progress | |
| 9 | Default backend host port is 8090 | 8080 is commonly taken on dev machines. Configurable in `.env`. |
| 10 | MDX is compiled client-side (`@mdx-js/mdx` `evaluate` in the browser) | Single-user local app, so no SEO or server-render need; the Go backend stays a thin file server with no Node dependency; edits show on refresh with no rebuild; components (and later interactive/simulator widgets) live next to React code. Cost: a larger JS chunk, loaded lazily only on lesson pages. |
| 11 | Content errors are collected, never fail-fast | Authoring feedback: one run lists every problem as `file: message`. |
| 12 | Startup exits non-zero on invalid content, but a running server hot-reloads and serves 503 with the error list | Fail loudly at boot; edit-and-refresh friendly in dev. Reload is a path/size/mtime fingerprint checked per request. |
| 13 | YAML via `go.yaml.in/yaml/v3` with unknown fields rejected | Typos in keys become errors. |
| 14 | `quiz.yaml` is optional per section; `multi_choice` needs >=2 correct (use `single_choice` otherwise) | |
| 15 | Quiz API never exposes answers; `ordering` options are shuffled per request | The authored order of an ordering question is its answer. |
| 16 | Section, lesson and question ids are slugs and globally unique; file/folder names are only for disk ordering | Stable keys for `lesson_progress` / `quiz_attempts`. |
| 17 | `labs/` is allowed at the content root but not yet validated | Reserved for simulator scenarios. |
| 18 | Quizzes are graded on the server | Answers never leave the server before grading (the quiz/queue payloads carry none, enforced by an automated test); one grading implementation serves quizzes and review; the client cannot forge a score. |
| 19 | Leitner boxes with 1/3/7/14/30-day intervals | Simple, explainable, needs no tuning data for a single learner; the spacing roughly doubles per box (a common Leitner schedule) so a mastered question fades to monthly. Wrong answers return to box 1 and are due immediately so misses resurface in the next review session. |
| 20 | `passed` (70%) is informational only | The app is soft-gated: the threshold only drives encouragement copy. Nothing may read it to lock, hide or restrict anything. |
| 21 | Single-user tables have no `user_id` | One implicit local profile; adding a user column would imply accounts we explicitly do not have. A future multi-user step would be a deliberate migration. |
| 22 | Quiz `score` counts exactly-correct questions; partial credit feeds only topic mastery | Keeps `quiz_attempts.score` an integer and the percentage easy to read, while multi_choice partial credit still informs weak-topic accuracy. |
| 23 | Review answers are logged in `review_answers`, not `quiz_attempts` | Review must not create attempts, but its answers still count toward topic mastery (otherwise a weak topic could never recover through review). |
| 24 | Topic accuracy: last 10 answers, linear recency weights (newest = n), weak < 70% with >= 3 answers | Recent performance dominates but one lucky answer cannot hide a pattern; mirrors the 70% quiz threshold. |
| 25 | Content ids are the source of truth; orphaned DB rows are ignored and never deleted | Content can be restructured without breaking progress; restoring a removed id brings its history back. |
| 26 | Added a second placeholder section (`01-sample-two`) | Needed to exercise "skip / continue to the next section" with a real next section; clearly marked placeholder. |
| 27 | Diagrams are declarative YAML (`content/diagrams/*.yaml`), not hand-written SVG per lesson | One renderer gives every diagram the same icons, link styles, legend, dark mode, responsive scaling, step player, accessibility and reduced-motion handling; authors write nodes/links/steps instead of coordinates-and-paths; diagrams stay reviewable as small diffs and can be validated; a design change (e.g. a new link look) is made once. Cost: layouts are limited to what the schema expresses. |
| 28 | Diagrams, glossary and component references are validated server-side at startup (and on reload) | The same fail-loudly rule as lessons: a typo in a node id or a `<Term id>` is reported with file and line before it can reach a reader, all errors at once, with `make validate-content` for authoring. Resolving packet paths in Go (served as `route`) means one implementation and a validator that rejects paths that skip a link. |
| 29 | `<Predict>` is ungraded and unstored | Prediction helps learning by making the reader commit before seeing the answer; recording or scoring it would turn a thinking aid into a test (and conflicts with soft gating). The answer is in the page source, which is fine for a personal course. Graded practice lives in section quizzes and review. |
| 30 | Link looks combine a colorblind-safe palette (Okabe-Ito) with distinct dash patterns and weights, defined once in one style map | No style depends on color alone; the legend is generated from the same map. |
| 31 | On phones the SVG scales to fit and text is enlarged (sublabels dropped) instead of scrolling horizontally | A cropped, scrollable diagram hid half of the topology with no cue; fitting keeps the whole picture visible while tooltips and narration carry detail. |
| 32 | Glossary names and aliases must be unique across terms | Search by alias must resolve to one entry; ambiguity is an authoring error. |
| 33 | Target release: the Arista VeloCloud SD-WAN **7.0 documentation set (7.0.x)**; 6.4.0 is the fallback reference | Evidence (read 2026-10-19): Arista's documentation library lists 7.0 guides and a 7.0.0 product bulletin; the 7.0 Administration Guide has a "What's New in Version 7.0.0"; Security Advisory 0183 (2026-09-22) lists Orchestrator 7.0.0.2 and below, so the train ships; 6.4.0 release notes confirm GA builds R6400-20250429-GA (2025-05-02) and LTS-candidate status. GA/LTS status of 7.0.0 is not confirmed (release notes unreadable), so it is marked VERIFY rather than asserted. |
| 34 | Research notes live in `content/reference/` with a mandatory claims table (claim, source URL, doc version, status VERIFIED / SECONDARY / VERIFY), enforced by the content validator | Keeps lessons honest: each technical claim has a row, and the status shows how well it is confirmed. The folder is exempt from the orphan rule because it is author material. |
